# 게임 발견 공장 — 자율 운영 프로토콜

> 오너(2026-11-06): "BB탄은 벽돌깨기에서, 랜덤다이스는 디펜스에서, 무한의 계단은 단순 투버튼에서 착안해 대박이 났다.
> 기존에 있는 걸 잘 조합하고 변형해서 새로운 걸 만들어내는 공장이었으면 좋겠다."
>
> 그래서 이 공장은 **아는 장르 2~3개의 핵심 재미 한 조각씩을 섞고, 한 번 비튼** 캐주얼 게임을 만든다.
> 장르 *규칙 조각*만 재료로 쓴다 — 특정 게임의 이름·캐릭터·아트·레벨·외형을 가져오지 않는다.

## 구조
- `arcade/core.ts` 공통 틀(결정적 시뮬레이션·입력·봇 실행) + `GENES`(장르 조각 목록)
- `arcade/games/<id>.ts` 게임 하나 = `GameDef` + 못하는 봇 + 잘하는 봇. `arcade/registry.ts`에 등록 — **지금 오너 앞에 있는 게임만** 둔다(아래 '폐기')
- `arcade/evaluate.ts` 봇 계기판 → `arcade/reports/eval.json`
- `arcade/play.ts` 브라우저 플레이어 · `arcade/cli-dashboard.ts` 계기판 → `arcade/reports/dashboard.html`
- `arcade/ab.json` A|B 라운드 · `arcade/STATE.md` · `arcade/BACKLOG.md` · `arcade/JOURNAL.md` · `arcade/experiments/NNNN-*.md`
- `tests/arcade.test.ts` 출시 게이트(결정성·규칙 3줄 이하·실력이 통함)

## 오너 피드백에서 나온 필수 기준 (0022, 9라운드 "둘 다 별로" — "조작이 불편, 목표가 너무 쉽게 보이고 계속해도 어떨지 단번에 느껴짐, 보기에 밋밋")
1. **손에 붙는 조작**: 화면에서 하고 싶은 걸 바로 한다(가리킨 곳으로 간다·끌어서 조준·누른 곳에 짓는다).
   조작을 일부러 묶는 비틀기(한쪽으로만 꺾기, 밀 때만 시간이 흐름 등)는 금지. 비틀기는 규칙·판·성장에서 한다.
2. **펼쳐짐**: 첫 화면에 모든 게 보이면 안 된다. 판이 흐르며 새 것이 나온다 — 새 적·새 능력·사건(보스·폭풍·습격)·판의 변화·새 구역.
   `reveals(s)`로 센다. **봇 판 2분 안에 4가지 이상**(계기판 "펼쳐짐 30초/60초/2분"). 다음에 뭐가 나올지 궁금하게 — 예고(실루엣·"다음 웨이브: ?")를 쓴다.
3. **풍성한 화면**: `arcade/juice.ts`를 반드시 쓴다 — 처치·피격·획득마다 파티클, 떠오르는 숫자/글자, 큰 사건엔 흔들림·번쩍.
   배경은 움직인다(`drift` 등), 주인공·적은 단순 원/네모가 아니라 컨셉에 맞는 실루엣. 스크린샷을 보고 "밋밋한가?"를 스스로 묻는다.

## 와우 포인트 (오너 2026-11-07, 11라운드 "둘 다 별로" 뒤) — 필수 기준 4
> "와우 포인트가 있으면 좋을 것 같다. 기획적으로 참신한 요소. 등불 마을은 '빛으로 비췄을 때만 동작한다'가 비슷했지만,
> 계속 비춰야 하는 피로도가 높아서 와우 포인트가 되지 못했다. 금방 뻔해짐, 화면이 아직 밋밋." · 다음 방향: "완전히 다른 장르"
4. **와우 포인트**: 게임마다 "어, 이게 돼?" 하는 참신한 규칙 하나를 한 문장으로 적는다(`twist`). 장르를 섞기만 한 것은 와우가 아니다.
   첫 30초 안에 플레이어가 그 규칙을 직접 겪어야 한다(설명이 아니라 경험).
   **피로 금지**: 와우를 쓰려면 화면을 계속 누르고 있어야 하는 구조(등불 마을)는 안 된다 — 한 번의 손짓이 오래 효과를 남겨야 한다.
5. **뻔해지지 않기**: '새로 나온 것'은 새 적·새 건물 같은 같은 동사의 변종이 아니라, **하는 일을 바꾸는 것**이어야 한다(새 전략·새 위험·판의 규칙 변화).
6. **화면 기준을 올린다**: 단색 도형 금지. 빛 번짐(shadowBlur/가산 합성)·잔상·충격파·움직이는 다층 배경·표정 있는 주인공. 스크린샷을 오너 눈으로 다시 보고, 지난 게임보다 확실히 나은지 묻는다.
- 12라운드는 지키기·키우기(디펜스) 계열을 쓰지 않는다 — 오너: "완전히 다른 장르". 아래 '취향 쪽/탐험 쪽' 규칙은 이 지시가 우선한다.

## 12라운드 "둘 다 별로" 이유 (오너 2026-11-08) — 필수 기준 7~8
> 와우가 약함 · 바로 재미가 안 옴 · 조작·손맛 · 목표·보상 부족 (넷 다)
7. **첫 3초 안에 재미**: 첫 손짓 한 번에 화면에서 큰 일이 일어나야 한다(쏟아짐·폭발·연쇄). 설명을 읽기 전에 손이 먼저 재미를 안다.
8. **목표와 보상이 눈에 보인다**: "끝없이 버티기 + 점수"만으로는 부족하다. 판마다 분명한 목표(예: N개 담기), 달성하면 별·축하·다음 판, 잘할수록 다음 판이 유리해지는 보상.

## 폐기 — 선택받지 못한 게임은 남기지 않는다 (오너 2026-11-07)
> "선택 받지 못한 아이디어는 폐기해서 보여주지마. 지금 다음 라운드 후보 게임들이 너무 많은거 같아. 재미없는건 폐기해."
- 라운드에서 진 게임(둘 다 별로면 둘 다)은 판정을 처리하는 사이클에 **`arcade/registry.ts`와 `arcade/games/`에서 지운다.**
  `ab.json`의 `discarded`에 id·이름·재료·이유만 남긴다(재료 사용 횟수는 계속 센다 → 같은 재료를 '새것'으로 다시 추천하지 않음).
- 계기판에는 **지금 라운드의 두 게임과 졸업한 게임만** 보인다. 후보 대기열(다음 라운드 후보)은 두지 않는다.
- 게이트를 못 넘은 새 게임도 레지스트리에 올리지 않고 지운다(실험 기록에 이유만).
- **오너가 직접 준 아이디어는 예외** (2026-11-08): 라운드가 열려 있어도 바로 만들어 `origin`(출처)을 달고 계기판의 '💡 오너 아이디어' 칸에 올린다. 그 라운드가 끝나면 이긴 쪽과 이 게임으로 다음 라운드(둘 다 별로면 이 게임 + 새 게임 하나).
- 라운드가 열려 있는(오너 답을 기다리는) 동안엔 **새 게임을 만들지 않는다** — 만들어 봐야 보여줄 자리가 없다.
  그 사이클은 BACKLOG의 지표·도구 항목만 하거나, 할 일이 없으면 아무것도 바꾸지 않고 끝낸다(이건 실패가 아니다, 연속 실패에 세지 않는다).
  24시간 넘게 답이 없으면 하루 한 번 알린다(4단계).

## 게임 하나의 조건 (게이트)
- 조작: 게임에 맞는 것이면 무엇이든(탭·꾹 누르기·좌우·드래그·스와이프…). 오너(2026-11-07): "굳이 원버튼을 고집할 필요 없어." 규칙 문장 **3줄 이하**, 첫 문장에 조작이 나온다.
- 결정적 시뮬레이션(같은 시드·같은 입력 → 같은 결과). 그림 그리기는 시뮬레이션과 분리.
- 봇 계기판: 숙련 격차(잘함 ÷ 못함 점수) ≥ 3, 못하는 봇 생존 ≥ 5초, 잘하는 봇 중앙값 30초~3분.
- "조합 + 비틀기"를 `genes`(2~3개)와 `twist`(한 문장)로 명시. 비틀기 없이 장르를 섞기만 한 것은 탈락.
- 디자인 컨셉(`art`) 필수. 게임 화면은 페이지 테마가 아니라 그 게임의 팔레트로 그린다.

## 한 사이클 (반드시 이 순서)
1. **동기화**: `git fetch origin factory && git checkout factory && git pull --rebase origin factory`, `npm ci`.
2. **읽기**: `arcade/STATE.md`, `arcade/BACKLOG.md`, `arcade/JOURNAL.md` 최근 3개, `arcade/ab.json`.
3. **정지 조건**: STATE `상태: BLOCKED`면 아무것도 바꾸지 말고 종료.
4. **오너 판정 처리 (최우선)**:
   - **졸업(최종 선택)** (오너 요청 2026-11-07): 오너가 고르면서 "더 디벨롭해줘"·"최종"·"구체화" 등으로 그 게임을 키우라고 하면 졸업이다.
     ① `ab.json`에 winner·`graduated` 기록, `champion = null`. ② `studio/<게임>/BRIEF.md`를 `studio/planet-guardian/BRIEF.md` 형식으로 쓴다
     (출발점 파일·오너가 고른 길·할 일·결과물 위치·가드레일). ③ `create_session`으로 **별도 세션**을 만들어 브리프를 맡긴다
     — 그 세션은 전문 게임 기획자 겸 개발자로 상용화 수준까지 다듬는다(공장은 그 게임을 더 손대지 않는다).
     ④ 빈 챔피언 자리: **이번 사이클의 새 게임 둘끼리** 다음 라운드를 연다(A·B 모두 새 아이디어). 그 뒤로는 다시 챔피언 방식. 채팅에 오너의 A|B 답이 있으면 `ab.json` 현재 라운드에 winner·이유 기록, `champion` 갱신,
   JOURNAL에 "A|B N라운드 판정". 오너가 단 이유(“둘 다 별로, ○○ 때문”)는 다음 게임 설계 기준으로 BACKLOG 맨 위에.
   진 게임은 같은 사이클에 폐기한다(위 '폐기').
   새 라운드를 연다: 챔피언이 있으면 A = 챔피언, B = 이번 사이클에 새로 만든 두 게임 중 봇 재미 추정 1위(나머지 하나는 폐기).
   챔피언이 비어 있으면(졸업 직후·둘 다 탈락 뒤) A·B 모두 이번 사이클에 새로 만든 두 게임.
   **오너 답을 기다릴 땐 링크를 항상 준다** (오너 요청 2026-11-08: "내 답을 기다릴땐 링크를 항상 줘"): 라운드가 열려 있는 동안의
   모든 사이클 요약·채팅 답·알림(PushNotification)의 **첫 줄에 계기판 전체 주소** https://derrick1119.github.io/derrickkim1119/arcade/ 를 넣는다.
   **오너 결정이 필요해지면 반드시 알린다** (오너 요청 2026-11-06): 새 라운드가 열렸을 때, 또는 열린 라운드가 24시간
   넘게 답이 없을 때(하루 한 번만), 또는 공장이 오너 승인 없이는 못 하는 일(제품 공개·규칙 큰 변경 등)에 막혔을 때
   `PushNotification`으로 "결정해 주세요: …"를 보내고, 사이클 요약 첫 줄도 "🔔 결정 필요:"로 시작한다.
   결정이 필요 없는 사이클엔 알림을 보내지 않는다.
5. **기본 업무 — 새 게임 둘** (오너 요청 2026-11-07): 오너가 판정해서 **새 라운드를 열어야 하는 사이클에만** 새 조합 게임 **2개**를 만든다(라운드가 열려 있으면 만들지 않는다). 각 게임에는 반드시
   디자인 컨셉(`art`: 컨셉 이름 · 분위기 한 줄 · 팔레트)을 입히고, 그 컨셉에 맞게 그리기(배경 모티프·도형·색)를 꾸민다.
   **둘 중 하나는 "취향 쪽", 하나는 "탐험 쪽"** (0022, 9라운드 "둘 다 별로" 뒤): 오너가 지금까지 이기게 한 게임은 전부
   궤도 수비 계열이다 — **지킬 대상(행성·기지·마을)이 있고, 사방에서 압박이 오고, 판 안에서 내 기지가 눈에 보이게 커진다.**
   진 게임들도 무작위 강화는 대부분 있었으므로 "강화"만으로는 부족하고 "지키고 키우는 내 것"이 핵심으로 보인다.
   취향 쪽 = 이 판타지를 다른 장르 조각(농사·교차로·덱·자동 전투·땅따먹기 등)으로 새로 짠 게임(궤도 수비의 재탕 금지).
   탐험 쪽 = 추천기에서 자유롭게. 오너가 "둘 다 별로"라고 하면 둘 다 탈락, 다음 사이클 새 게임 둘로 다음 라운드.
   **조합은 `npx tsx arcade/ideas.ts`의 추천에서 고른다** (오너 요청 2026-11-07, 다양성): 새 게임 둘은 각각
   **아직 안 써 본 재료를 하나 이상** 쓰고, 둘이 같은 핵심 놀이를 공유하지 않는다. 말이 안 되는 짝은 건너뛰고 다음 후보로.
   오너 선택 경향(같은 핵심 위에 저절로 도는 성장 층 — 처치·채굴 → 강화·건설)은 성장 재료 선택에 반영한다. 조작은 원버튼에 묶이지 않는다.
   재료가 부족하면 `arcade/core.ts`의 GENES에 장르 조각을 더 넣는다(장르 이름만, 특정 게임 이름·캐릭터 금지).
   BACKLOG의 다른 항목(다듬기·지표)은 새 게임 둘을 만든 뒤 여유가 있을 때.
   코드 수정 *전에* `arcade/experiments/NNNN-제목.md`에 조합·비틀기·가설·**폐기 기준**을 쓴다.
6. **측정**: `npx tsx arcade/evaluate.ts`, `npm run verify`. 게이트 미달이면 수치를 보고 한 번 다듬고, 그래도 미달이면
   폐기한다(레지스트리·코드에서 지우고 실험 기록에 이유). 이것도 성과다.
7. **새 아이디어 1~3개**를 BACKLOG에 (조합표에서 아직 안 쓴 짝, 오너 이유에서 나온 것 우선).
8. **기록**: JOURNAL 맨 위 항목, STATE 갱신(게임 목록·봇 지표·라운드·연속 실패 수).
9. **계기판 갱신** (매 사이클): `npx tsx arcade/cli-dashboard.ts --cycle NNNN` → `arcade/reports/dashboard.html`과
   **`web/public/arcade/index.html`**(GitHub Pages)이 함께 만들어진다. push하면 Pages가 자동 배포 →
   오너 주소: https://derrick1119.github.io/derrickkim1119/arcade/ (오너 결정 2026-11-07: 공개 페이지로 운영, 승인 창 없음).
   아티팩트(`publish_files`)는 게시마다 오너 승인 창이 떠서 **쓰지 않는다**. 오너에게 알릴 땐 Pages 주소를 준다.
   push 뒤 GitHub Actions의 deploy(pages.yml) 실행이 success인지 확인한다(이 환경에선 github.io에 직접 접속 불가). 실패하면 JOURNAL에 적는다.
10. **푸시**: 커밋 메시지 "발견 NNNN: <요약>", `git push -u origin factory`. 거절되면 `git pull --rebase origin factory` → verify → push.

## 절대 규칙
- `npm run verify` 실패 상태로 push 금지. 테스트 약화·삭제·skip 금지.
- 발명 공장 파일(`factory/`, `engine/`의 기존 동작, 루트 CLAUDE.md 발명 공장 절) 수정 금지. 공유 파일은 *추가만*.
- 런타임 의존성 추가 금지. 게임 하나의 번들은 gzip 30KB 이하.
- 외부 서비스 가입·결제·공개 게시 금지. 기존 게임의 이름·캐릭터·아트·레벨을 가져오지 않는다.
- force push 금지. `factory` 브랜치에만 push. PR·main 병합은 오너 요청 시에만.
- 연속 3사이클 실패(verify 실패로 커밋 못 함, 진전 없음)면 STATE `상태: BLOCKED` + 이유를 "오너에게"에 쓰고 종료.
- 사이클당 코드 diff 약 800줄 이내(게임 하나가 대개 200~300줄, 사이클당 둘).
